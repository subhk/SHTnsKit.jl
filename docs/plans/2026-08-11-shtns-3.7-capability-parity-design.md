# SHTns 3.7 Capability-Parity Design

Date: 2026-08-11

## Objective

Provide idiomatic Julia capability parity with the mathematical feature surface
of SHTns 3.7 on CPU, CUDA, AMDGPU, MPI/CPU, MPI/CUDA, and MPI/AMDGPU.

Parity covers grids, conventions, layouts, scalar/vector/QST transforms,
degree-truncated and fixed-order transforms, batch transforms, local evaluation,
spectral operators, rotations, and Float32/Float64 execution. It does not require
C ABI, allocation, lifecycle, build-information, profiling, or identical
performance-policy APIs.

## Public API and dispatch

Mathematical operations are the primary API. Execution is selected through the
typed `CPU()` and `GPU()` markers and through array storage:

```julia
analysis(cfg, field)                  # infer from storage
analysis(CPU(), cfg, field)
analysis(GPU(), cfg, field)
```

Existing `gpu_*` and `dist_*` functions remain supported as compatibility
wrappers. A normal `Matrix` selects CPU, CUDA and AMDGPU arrays select their
respective extensions, a `PencilArray` selects MPI, and a `PencilArray` wrapping
GPU storage selects MPI+GPU.

`GPU()` does not contain a vendor symbol. An existing GPU array determines its
backend by type. Moving a host array with `to_device(GPU(), array)` selects the
only loaded functional backend; when more than one is available, callers must
provide an array prototype so the package cannot silently choose a vendor.

Validation, normalization, coefficient layout, truncation, pole ordering, and
error semantics are shared. Computation remains concrete:

- CPU uses Julia and FFTW.
- CUDA and AMDGPU share portable KernelAbstractions kernels but keep separate
  allocation, FFT, synchronization, device, and memory adapters.
- MPI uses PencilArrays and MPI collectives.
- MPI+GPU applies GPU kernels to GPU-resident local partitions.

`SHTConfig` remains host-owned. GPU extensions lazily cache device copies of
quadrature data, normalization scales, Wigner matrices, and Legendre tables.

## Mathematical surface

The parity contract includes:

- Gauss, on-the-fly Gauss, Fejer regular, and pole-inclusive
  Clenshaw-Curtis grids.
- Degree and order truncation, azimuthal periodicity (`mres`), latitude-major
  and longitude-major storage, and north/south-first ordering.
- Orthonormal, four-pi, Schmidt, real normalization, and optional
  Condon-Shortley phase.
- Real and complex scalar, spheroidal/toroidal, and QST transforms.
- Full-grid, degree-truncated (`_l`), fixed-order (`_ml`), batch, point,
  latitude, and gradient evaluation.
- Spectral multiplication operators and every SHTns rotation form.
- Float32 and Float64 execution.

All transforms compute internally with orthonormal harmonics including the
Condon-Shortley phase. Analysis converts canonical coefficients into the
configuration's requested convention before returning. Synthesis converts input
coefficients into the canonical convention before computation. CPU, GPU, and MPI
use the same conversion rules.

Grid names describe quadrature rather than performance strategy. `:regular`
retains its midpoint nodes and uses Fejer weights. `:regular_poles` uses
Clenshaw-Curtis weights. SHTns `sht_reg_fast` and `sht_reg_dct` map to the same
Julia mathematical capability because their difference is algorithm selection.

Dense and packed coefficient formats remain supported. Both spatial memory
orientations are accepted through `AbstractMatrix` storage without changing
logical `(theta, phi)` indexing. Backend conversion and redistribution occur only
at API boundaries.

`SH_to_grad_point` evaluates the radial coefficients passed as `DrSlm` rather
than discarding them. Existing internal implementations that correspond to
public SHTns mathematical operations become documented public APIs.

## Backend execution

The existing CUDA extension and a new AMDGPU extension share only concrete
KernelAbstractions mathematical kernels. Field and coefficient arrays remain on
the selected device. Small immutable setup data may be constructed on the host
and cached on-device. Float32 and Float64 caches are distinct.

MPI execution follows these rules:

- Fixed-order and diagonal operators execute on ranks that own the modes.
- Latitude and point evaluation reduce local partial sums.
- Scalar, vector, and QST transforms use distributed FFT and Legendre work.
- Rotations that mix orders redistribute or gather required spectral bands.
- Truncated transforms do not communicate degrees above their limits.

The same algorithms operate on GPU-backed `PencilArray`s. GPU-aware MPI is used
when available; otherwise explicit pinned-host staging is permitted while public
inputs and outputs remain device-resident.

## Errors

A requested backend never silently falls back to CPU. `GPU()` without a
functional CUDA or AMDGPU extension raises a capability error. Existing
`gpu_*_safe` wrappers may retain their explicitly documented fallback behavior.

All backends share dimension, truncation, `mres`, storage, normalization, grid,
and precision validation. Unsupported combinations fail at the API boundary.
MPI validation is collective so an error on one rank cannot strand other ranks.

## Verification

Verification has three layers:

1. Independent mathematical checks using analytic modes, direct spherical-
   harmonic sums, and quadrature identities.
2. Small reference cases generated by SHTns 3.7 for every convention, grid,
   transform family, local evaluator, operator, and rotation.
3. Cross-backend equivalence for CPU, CUDA, AMDGPU, MPI/CPU, MPI/CUDA, and
   MPI/AMDGPU with precision-specific tolerances.

The parity matrix is executable: a capability is complete only when its public
API and required backend tests exist. Float32 and Float64 use separate tolerances
and high-degree stability cases.

Local verification can cover CPU, MPI, extension loading, and GPU compilation or
fallback behavior. Runtime certification for CUDA, AMDGPU, and their MPI
combinations requires matching hardware CI runners. Unexecuted hardware cells
remain explicitly marked unverified.

## Delivery sequence

Implementation proceeds in vertical slices, each completed across all required
backends before the next begins:

1. Executable parity inventory and public API contract.
2. Grid quadrature, normalization, phase, real normalization, layout, and
   precision semantics.
3. Real and complex scalar transforms.
4. Spheroidal/toroidal and QST transforms.
5. Degree-truncated, fixed-order, and batch transforms.
6. Point, latitude, and gradient evaluation.
7. Spectral operators and rotations.
8. Combined MPI+GPU execution, documentation, and the complete verification
   matrix.
